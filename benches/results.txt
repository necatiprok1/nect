           bytecode  the VM interpreter loop alone (NECT_NO_JIT=1)

         prints exactly what `nect run` prints.

Reading the numbers:
  - "vs Python" is the native binary against CPython. It is dominated by process
    startup on the small rows (~2ms Nect/cc binary vs ~18ms CPython here): a
    7x-30x wall-clock ratio on a 20ms benchmark is really the same ~30x-250x
    compute ratio the heavy rows show without the masking.
  - The heavy rows are large enough that startup is noise. There the native
    binary runs 50x-250x faster than CPython and 1.2x-1.8x faster than the
    in-process JIT, mostly because C code keeps the hot loop's accumulators in
    registers across the whole loop instead of re-reading them per call.
  - heavy/dot_product and heavy/knn_distance are unrolled four ways *in Nect
    source*; the same unrolling is what lets the C compiler keep four
    independent multiply-add chains in flight. The JIT gets the same benefit,
    which is why it moves in the same direction (1.8x over bytecode-JIT).
  - relu_activation is the one row where the JIT is faster than the native
    binary (0.9x): Cranelift compiles the hot function once at startup while
    this row's total is small enough that the ~2ms process+startup share is
    comparable to the compute itself.

Process overhead (empty program), for interpreting the numbers:
  native (nect build binary / nect run):  0.0026s
  Python:                                   0.0199s
  Trivial /usr/bin/true:                    ~0.0013s

Key takeaways:
  - `nect build` produces standalone executables whose output is identical to
    the VM's (parity ok on every row; pinned by tests/aot_tests.rs).
  - Compute-bound numeric work: 50x-250x over CPython, 1.2x-1.8x over the JIT.
  - The JIT remains the default engine: it needs no C compiler, handles a wider
    subset (arrays, strings, any builtin), and startup is immediate.
  - Every CPython row is also slower than the Nect bytecode VM on arithmetic
    (Loop Sum, Factorial), so even without native code the language does not
    lose to Python here.

History (same machine, earlier runners; indicative):
  Phase 1    fib 0.944 -> 0.190s   loop 0.039 -> 0.0090s
  Phase 2    fib 0.190 -> 0.128s   loop 0.0090 -> 0.0040s
  Phase 2.3  fib 0.128 -> 0.110s   loop unchanged
  Phase 3    fib 0.110 -> 0.0088s  loop 0.0043 -> 0.0042s (module prefix JIT)
  Language work (builtins library, arrays, loop keywords, UTF-8 strings):
             fib and loop unchanged within noise; no benchmark file changed.
  C backend (nect build):  fib 0.0089 -> 0.0043s; heavy suite added, where
             native beats CPython by 50x-250x and the JIT by 1.2x-1.8x.
  for-loop stack leak fixed (two operands per iteration pushed onto the VM's
             operand stack): heavy for-loops no longer grow memory without bound
             (650MB -> flat over 3M iterations).

Note: sub-millisecond differences on this machine are close to noise; a delta
below ~0.0003s should be re-measured before it is believed.
